# 11단계: 사용자 권한 격리 통합 테스트

이번 단계의 목표는 실제 PostgreSQL 위에서 사용자별 데이터 격리가 지켜지는지 확인하는
것입니다. 서비스가 로그인 기반으로 확장되면 “사용자 A의 데이터를 사용자 B가 볼 수 없는가?”가
핵심 보안 조건이 됩니다.

  - 사용자 A의 캐릭터, 기억, 대화방을 만듭니다.

## 검증하는 보안 조건

이번 테스트는 다음 조건을 확인합니다.

1. 다른 사용자의 캐릭터를 상세 조회할 수 없다.
2. 다른 사용자의 캐릭터에 자기 기억을 연결할 수 없다.
3. 다른 사용자의 기억 ID를 알아도 조회할 수 없다.
4. 다른 사용자의 `conversation_id`를 알아도 대화를 이어갈 수 없다.

ID는 UUID라 추측하기 어렵지만, 보안 설계에서는 “ID를 알게 되어도 권한이 없으면 접근하지
못한다”가 더 안전한 기준입니다.

## 테스트 흐름

```text
사용자 A 회원가입
사용자 B 회원가입
  → A가 캐릭터 생성
  → A가 캐릭터 기억 생성
  → A가 캐릭터와 대화 생성
  → B가 A의 캐릭터 조회 시도 → 거부
  → B가 A의 캐릭터에 기억 생성 시도 → 거부
  → B가 A의 기억 조회 시도 → 거부
  → B가 A의 대화방 이어가기 시도 → 거부
```

## 왜 라우터가 아니라 서비스 계층에서 검증하나?

라우터는 JWT를 통해 “현재 사용자”를 찾고, 서비스 계층은 그 사용자 ID를 기준으로 실제
권한 규칙을 적용합니다. 이번 테스트는 실제 DB와 서비스 계층을 함께 검증해 소유권 조건이
쿼리와 비즈니스 규칙에 제대로 들어갔는지 확인합니다.

HTTP 상태 코드 변환은 기존 라우터 테스트가 맡고, 이번 테스트는 도메인 예외가 올바르게
발생하는지 확인합니다.

## 이번 단계의 한계

- HTTP 라우터까지 통과하는 권한 격리 E2E는 아직 아닙니다.
- 관리자 권한이나 공개 캐릭터 정책은 아직 단순합니다.
- 대화방 목록 조회 API는 아직 없기 때문에 대화방 목록 격리는 별도 검증하지 않았습니다.

DB 통합 테스트로 확인합니다.
